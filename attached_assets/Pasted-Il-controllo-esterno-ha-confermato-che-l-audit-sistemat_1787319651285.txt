# 2. PROBLEMA DA RISOLVERE

Attualmente risulta:

```ts

```

mentre i percorsi normali osservati sono circa:

* Piano standard: 14 model calls;
* Piano `lactose`: 7 model calls.

42 è quindi troppo permissivo.

L’obiettivo non è soltanto avere un limite tecnico, ma avere un **hard cap economicamente sensato**.

# 4. PRIORITÀ DEL BUDGET

L’ordine deve essere:

1. sicurezza allergeni;
2. risposta strutturalmente valida;
3. completamento del piano;
4. varietà.

La varietà NON può giustificare il raddoppio o triplicamento del costo.

Se un piano è:

* completo;
* strutturalmente valido;
* compatibile con tutti gli allergeni;

ma leggermente meno vario, preferisci quel piano a una nuova generazione completa.

# 5. RIDUCI `MAX_MEAL_PLAN_MODEL_CALLS`

Il valore 42 deve essere ridotto significativamente.

Non impostare un nuovo valore arbitrariamente.

Calcola il **minimo hard cap sostenibile** sulla base dei test.

Come ordine di grandezza, se il percorso standard richiede realmente circa 14 chiamate, un valore nell’area:

```text
16–18
```

sarebbe molto più coerente.

Ma scegli il valore finale sulla base dei percorsi reali.

Documenta esattamente perché quel valore è sufficiente.

# 6. UNICO BUDGET CUMULATIVO PER RICHIESTA

Ogni singola azione dell’utente:

* Genera Piano;
* Genera alternativa;

deve avere un unico budget.

Tutte le chiamate OpenAI devono consumare lo stesso contatore:

* generazione;
* malformed response retry;
* format retry;
* constraint retry;
* local repair;
* variety retry.

Nessuna funzione deve creare un nuovo budget interno per aggirare il cap.

Deve valere sempre:

```ts
modelCalls <= MAX_MEAL_PLAN_MODEL_CALLS
```

# 8. CONTROLLA IL BUDGET PRIMA DELLA MODEL CALL

Prima di ogni chiamata OpenAI:

1. calcola il residuo;
2. verifica che l’operazione sia consentita;
3. incrementa/riserva la chiamata;
4. invoca OpenAI.

Mai:

```text
OpenAI
→ incremento successivo
```

# 9. NON AVVIARE OPERAZIONI CHE NON POSSONO COMPLETARSI

Aggiungi una logica esplicita equivalente a:

```ts
remainingModelCalls()
canAffordModelCalls(requiredCalls)
```

Se un’operazione richiede più chiamate del residuo disponibile, non iniziarla.

Esempio:

```text
budget residuo = 3
rigenerazione completa = 14

=> NON iniziare la rigenerazione
```

# 10. VARIETÀ = BEST EFFORT

Rivedi:

```ts
MAX_LOCAL_VARIETY_REPAIRS
```

e:

```ts
MAX_VARIETY_GENERATION_RETRIES
```

I local repair possono essere mantenuti soltanto se:

* consumano il budget globale;
* sono limitati;
* non sottraggono margine necessario alla sicurezza.

Per il full variety retry:

* preferibilmente eliminarlo;
* oppure consentirlo soltanto quando il budget residuo permette di completarlo integralmente.

Non rigenerare una settimana intera soltanto per migliorare una lieve ripetizione.

# 11. NON SACRIFICARE LA SICUREZZA

Se il budget è quasi esaurito e viene rilevata una violazione allergene:

* NON restituire il piano;
* NON disattivare il constraint;
* NON trasformare l’allergene in best effort.

Se invece:

* il piano è sicuro;
* è completo;
* è strutturalmente valido;
* presenta soltanto qualche ripetizione;

può essere restituito senza ulteriori chiamate di varietà.

# 12. ERRORE A BUDGET ESAURITO

Mantieni o usa un errore tipizzato come:

```text
AI_MODEL_CALL_BUDGET_EXHAUSTED
```

Il frontend deve ricevere un messaggio comprensibile, per esempio:

```text
Non è stato possibile completare il piano in modo affidabile. Riprova.
```

Non mostrare:

* 16/18 chiamate;
* token;
* stack trace;
* dettagli OpenAI.

# 13. NON MODIFICARE LE QUOTE GIORNALIERE

Non cambiare:

```text

```

o il numero di Piano Pasti che una famiglia può generare al giorno.

Questo mandato riguarda soltanto il costo di **una singola richiesta**.
