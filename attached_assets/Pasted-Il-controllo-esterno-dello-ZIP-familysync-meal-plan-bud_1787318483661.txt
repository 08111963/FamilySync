Attualmente però risulta:


Questo valore è troppo alto rispetto ai percorsi normali osservati:

* piano con solo `lactose`: circa 7 chiamate.

Un tetto di 42 consente teoricamente fino a tre volte il costo di un piano standard e rende poco efficace il controllo dei costi.

L'obiettivo di questo mandato è quindi **ridurre e ottimizzare il budget OpenAI senza modificare la sicurezza alimentare, gli allergeni o la varietà già corretta**.

Questo mandato riguarda esclusivamente:

* retry;

* hard cap;
* comportamento a budget quasi esaurito.

# 2. RICOSTRUISCI IL COSTO REALE DELLA PIPELINE

Prima di modificare il valore 42, ricostruisci esattamente quante chiamate OpenAI richiede ogni percorso.

# 3. PRINCIPIO OBBLIGATORIO

Usa questa priorità:

1. SICUREZZA ALIMENTARE;
2. validità strutturale della risposta;
3. completamento del piano;
4. varietà.

La varietà è **best effort**.

Non è accettabile raddoppiare o triplicare il costo di una generazione soltanto per avere un piano più vario.

Se un piano è:

* strutturalmente valido;
* sicuro rispetto agli allergeni;
* completo;

ma presenta qualche ripetizione, deve essere preferito a una nuova generazione completa costosa.

# 4. RIDUCI IL TETTO 42

Non mantenere:

```ts
MAX_MEAL_PLAN_MODEL_CALLS = 42;
```

soltanto perché permette tutti i retry teoricamente possibili.

Calcola il valore minimo ragionevole sulla base dei test.

Come ordine di grandezza:

```text
16–18 chiamate
```

è molto più coerente con un percorso standard da circa 14 chiamate.

Non impostare automaticamente 18: scegli il valore finale in base alla pipeline reale e documentalo.

Il risultato deve comunque essere **sensibilmente inferiore a 42**.

# 5. UN SOLO BUDGET GLOBALE PER CLICK

Ogni pressione dell'utente su:

* Genera Piano;
* Genera alternativa;

deve avere un unico budget cumulativo.

Devono consumare lo stesso contatore:

* chiamate normali;
* format retry;
* malformed JSON retry;
* constraint retry;
* local variety repair;
* eventuale full variety retry.

Nessuna funzione deve poter creare un nuovo contatore e aggirare il limite.

Deve valere sempre:

```ts
modelCalls <= MAX_MEAL_PLAN_MODEL_CALLS
```

# 6. CONTA PRIMA DI CHIAMARE OPENAI

Prima di ogni invocazione OpenAI:

1. controlla budget residuo;
2. verifica che la chiamata sia consentita;
3. incrementa atomicamente/logicamente il contatore;
4. effettua la richiesta.

Non fare:

```text
chiamata OpenAI
→ poi incremento
```

Il limite deve essere impossibile da superare anche in caso di errore.

# 7. NON INIZIARE OPERAZIONI CHE NON POSSONO FINIRE

Questa parte è importante.

Se una determinata operazione richiede più chiamate del budget residuo, non deve essere iniziata.

Esempio:

```text
budget residuo = 3
full retry della settimana = circa 14
```

Non iniziare la rigenerazione completa sapendo che non potrà terminare.

Aggiungi helper espliciti se necessario, per esempio:

```ts
canAffordModelCalls(requiredCalls)
remainingModelCalls()
```

# 8. RIDUCI IL COSTO DELLA VARIETÀ

Controlla:

```ts
MAX_LOCAL_VARIETY_REPAIRS
```

e:

```ts
MAX_VARIETY_GENERATION_RETRIES
```

La varietà non deve consumare gran parte del budget.

Preferenza:

* prompt corretto;
* temi giornalieri;
* memoria inter-giorno;
* rilevamento duplicati;

prima di:

* local repair;
* rigenerazione completa.

## Local repair

Può essere mantenuto, ma:

* deve consumare il budget globale;
* deve essere limitato;
* non deve partire se il margine è necessario per eventuali retry di sicurezza.

## Full variety retry

Valuta seriamente di eliminarlo.

Se viene mantenuto, deve essere eseguito soltanto quando:

* il budget residuo permette di completare l'intera nuova generazione;
* esiste una motivazione forte;
* non riguarda soltanto una lieve ripetizione.

In generale preferisco **non rigenerare tutta la settimana per sola varietà**.

# 9. RISERVA IL MARGINE ALLA SICUREZZA

Il margine oltre il percorso normale deve essere utilizzato principalmente per:

* violazione allergene;
* risposta malformata/non validabile;
* errore strutturale recuperabile.

Non per rendere il menu esteticamente più vario.

Esempio concettuale:

```text
Percorso standard ≈ 14
Hard cap = 17

Margine = 3
```

Queste 3 chiamate devono essere utilizzabili per recovery indispensabili.

Non devono essere consumate tutte preventivamente dalla varietà.

# 10. COMPORTAMENTO A BUDGET ESAURITO

Quando il budget termina:

NON:

* effettuare una chiamata extra;
* restituire un piano con allergeni incompatibili;
* ignorare un errore di validazione;
* nascondere il problema.

Usa un errore tipizzato, per esempio quello già esistente:

```text
AI_MODEL_CALL_BUDGET_EXHAUSTED
```

e un messaggio utente comprensibile.

Esempio:

> Non è stato possibile completare il piano in modo affidabile. Riprova.

Non mostrare all'utente il numero tecnico di chiamate.

# 11. CASO VARIETÀ CON BUDGET ESAURITO

Caso specifico:

* piano completo;
* allergeni rispettati;
* risposta valida;
* qualche ripetizione;
* nessun budget residuo.

In questo caso NON fallire automaticamente soltanto per varietà.

La varietà è best effort.

Se il piano supera le verifiche di sicurezza obbligatorie, può essere consegnato con advisory interno.

Diverso il caso di violazione allergene:

* mai consegnare il piano;
* anche se il budget è esaurito.
