Dopo il deploy della correzione sulla varietà generale dei pranzi, il risultato è nettamente migliorato: non viene più generata pasta quasi ogni giorno.

Resta però un difetto specifico: vengono ancora prodotti nella stessa settimana **piatti semanticamente quasi identici**, anche se appartengono formalmente a categorie leggermente diverse.

Caso reale osservato in produzione:

```text
25/08
Risotto al limone con salmone e fagiolini

28/08
Riso al limone con salmone e zucchini saltati
```

Per l'utente questi due piatti sono sostanzialmente duplicati:

```text
riso + limone + salmone
```

Cambiare:

* risotto → riso;
* fagiolini → zucchine;

NON rappresenta una variazione sufficiente del piatto principale.

Questo mandato deve correggere esclusivamente questo difetto residuo.

NON fare deploy.

# 1. NON MODIFICARE LE CORREZIONI GIÀ FUNZIONANTI

NON modificare:

* allergeni;
* normalizzazione constraints;
* allowlist;
* sicurezza alimentare;
* `MAX_MEAL_PLAN_MODEL_CALLS = 28`;
* quote giornaliere;
* local repair massimo già impostato;
* rotazione deterministica delle famiglie di pranzo;
* UI;
* database.

La rotazione delle famiglie appena implementata deve rimanere.

# 2. RIPRODUCI IL CASO REALE

Aggiungi questo fixture:

```text
Risotto al limone con salmone e fagiolini
Riso al limone con salmone e zucchini saltati
```

Il sistema deve identificarli come **near semantic duplicate**.

Non considerarli diversi soltanto perché:

```text
risotto != riso
fagiolini != zucchine
```

La struttura principale è:

```text
cereale/base = riso
profilo/preparazione = limone
proteina = salmone
```

# 3. NORMALIZZA LE FAMIGLIE EQUIVALENTI

Introduci una normalizzazione semantica deterministica.

Esempi:

```text
riso
risotto
riso integrale
riso basmati
```

devono poter essere ricondotti alla macro-base:

```text
rice
```

quando serve al controllo anti-duplicazione.

Analogamente, valuta equivalenze sensate come:

```text
pasta
pasta integrale
spaghetti
penne
fusilli
```

→ macro-base `pasta`

Non usare questa normalizzazione per modificare il nome visualizzato del piatto.

Serve esclusivamente al controllo di varietà.

# 4. FIRMA SEMANTICA DEL PIATTO

Per ogni pranzo crea una firma almeno su quattro dimensioni:

```text
macro_carbohydrate
main_flavour_or_preparation
main_protein
meal_structure
```

Esempio:

```text
Risotto al limone con salmone e fagiolini

macro_carbohydrate = rice
main_flavour = lemon
main_protein = salmon
meal_structure = grain_main
```

e:

```text
Riso al limone con salmone e zucchini

macro_carbohydrate = rice
main_flavour = lemon
main_protein = salmon
meal_structure = grain_main
```

Le due firme devono risultare equivalenti o con similarità sufficientemente alta da essere considerate duplicate.

# 5. CONTORNI SECONDARI NON DEVONO NASCONDERE IL DUPLICATO

Ignora ai fini della firma principale differenze secondarie come:

* insalata;
* pomodori;
* fagiolini;
* zucchine;
* broccoli;
* rucola;
* olio EVO;
* basilico;
* aglio;
* prezzemolo;

quando il nucleo principale del pasto rimane identico.

Esempio:

```text
riso + limone + salmone + fagiolini
riso + limone + salmone + zucchine
```

deve essere considerato lo stesso pattern principale.

# 6. NON BASTA CONTROLLARE LA FAMIGLIA

Il checker deve mantenere separati almeno:

```text
family
base/preparation
protein
semantic signature
```

La famiglia serve a evitare:

```text
pasta 6/7
```

La firma serve a evitare:

```text
riso + limone + salmone
risotto + limone + salmone
```

Sono due problemi diversi.

# 7. PIANIFICAZIONE DETERMINISTICA PIÙ SPECIFICA

La rotazione preventiva non deve scegliere soltanto:

```text
pasta
riso
legumi
couscous
...
```

Aggiungi anche un **profilo-obiettivo** per il pranzo.

Esempio concettuale:

```text
Lunedì:
family = pasta
protein = fish
profile = tomato

Martedì:
family = rice
protein = fish
profile = lemon

Mercoledì:
family = legumes
protein = legumes
profile = soup

Giovedì:
family = couscous
protein = legumes
profile = vegetables

Venerdì:
family = grain
protein = poultry
profile = mediterranean

Sabato:
family = polenta
protein = poultry
profile = stew

Domenica:
family = quinoa
protein = legumes
profile = vegetables
```

Non devono essere necessariamente questi valori.

Il principio è che **due giorni non ricevano lo stesso tripletto principale**.

La pianificazione deve essere locale/deterministica e NON aggiungere chiamate OpenAI.

# 8. EVITA ANCHE PROTEINA + PROFILO RIPETUTI

In un normale piano mediterraneo senza allergeni, evita nella stessa settimana combinazioni come:

```text
salmone + limone
salmone + limone
```

anche se un giorno c'è riso e un altro risotto.

Best effort:

```text
same main protein + same main flavour/preparation <= 1
```

quando il pool disponibile lo permette.
