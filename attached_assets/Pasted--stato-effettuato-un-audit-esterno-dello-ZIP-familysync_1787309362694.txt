# 1. PROBLEMA PRINCIPALE — DIET E ALLERGIES SEGUONO PERCORSI DIVERSI

Attualmente:

`mealPlanPreferencesContainHealthData()`

considera:

* allergies;
* alcune notes;

ma non `diet`.

Di conseguenza:

`preferences.diet = "senza lattosio"`

e:

`preferences.allergies = "lattosio"`

non ricevono necessariamente le stesse protezioni.

Inoltre:

`usesMealPlanIngredientAllowlist()`

attualmente restituisce true quando:

* è richiesto gluten-free;
* oppure `mealPlanPreferencesContainHealthData()` restituisce true.

Questo significa che:

* allergies = "Lattosio" → allowlist;
* diet = "senza lattosio" → può NON avere allowlist;
* diet = "senza glutine" → allowlist tramite il controllo glutine.

Questa divergenza deve essere eliminata.

# 2. CREA UNA NORMALIZZAZIONE CANONICA DEI VINCOLI

Crea una funzione pura centrale, per esempio:

`normalizeMealPlanConstraints(preferences)`

che trasformi tutti gli input in una struttura canonica.

Esempio concettuale:

```ts
{
  dietaryPatterns: [
    "mediterranean"
  ],

  exclusions: [
    "gluten",
    "lactose"
  ],

  healthDerived: true | false,

  source: {
    diet: "...",
    allergies: "...",
    notes: "..."
  }
}
```

Non è obbligatorio usare esattamente questa interfaccia, ma deve esistere UNA sola interpretazione centrale.

Normalizza almeno:

## Glutine

Devono convergere allo stesso vincolo:

* senza glutine;
* gluten free;
* gluten-free;
* glutine;
* celiaco;
* celiaca.

Vincolo canonico:

`gluten`

## Lattosio

Devono convergere allo stesso vincolo:

* senza lattosio;
* lattosio;
* intolleranza al lattosio;
* intollerante al lattosio.

Vincolo canonico:

`lactose`

Non duplicare questa classificazione in più regex scollegate.

# 3. SEPARA DIETE ED ESCLUSIONI

Le diete devono rappresentare pattern alimentari, per esempio:

* mediterranea;
* vegetariana;
* vegana;
* pescetariana;
* chetogenica/low carb;
* halal.

Le esclusioni devono rappresentare alimenti/componenti da evitare:

* glutine;
* lattosio;
* latte;
* uova;
* arachidi;
* frutta a guscio;
* pesce;
* ecc.

L'utente può continuare a scrivere “senza glutine” o “senza lattosio” nel campo Dieta per compatibilità con la UI attuale, ma internamente deve essere trasformato nel relativo `exclusion`.

Non deve esistere un comportamento differente in base al campo dal quale proviene.

# 4. CORREGGI compatibleMealIngredients()

Attualmente il codice costruisce:

```ts
const declaredAllergies = normalizedPreferences
  .split(/[^a-z0-9]+/)
```

dove `normalizedPreferences` contiene:

* diet;
* allergies;
* notes.

Questo è errato.

Non trattare ogni parola delle preferenze come allergene.

Esempio:

`senza glutine`

non deve produrre una blacklist generica delle parole:

* senza;
* glutine.

In particolare non deve eliminare ingredienti sicuri come:

* pane senza glutine;
* fette biscottate senza glutine;
* biscotti senza glutine.

La lista degli ingredienti deve essere filtrata usando i VINCOLI CANONICI, non i token grezzi dell'intera frase.

# 5. SENZA GLUTINE — AMPLIA LA LISTA SICURA

La `SAFE_MAIN_INGREDIENTS` attuale contiene pasta e pane normali ma non equivalenti gluten-free sufficienti.

Aggiungi alternative esplicite e verificabili, per esempio:

* pasta senza glutine;
* pasta di mais senza glutine;
* pasta di riso senza glutine;
* pane senza glutine;
* couscous di mais senza glutine, solo se la denominazione è considerata sicura dal validatore;
* gnocchi senza glutine, solo se esplicitamente dichiarati tali.

Mantieni anche:

* riso;
* quinoa;
* polenta di mais;
* patate;
* legumi.

Non considerare automaticamente sicuro un prodotto trasformato soltanto perché è “di riso” o “di mais” se la policy attuale richiede esplicitamente la dicitura “senza glutine”.

La lista deve restare coerente con `validateMealPlanConstraints()`.

# 6. CORREGGI L'ORDINE DEL FILTRO GLUTEN-FREE

Un ingrediente come:

`pane senza glutine`

deve essere riconosciuto come sicuro PRIMA di applicare eventuali esclusioni lessicali.

Aggiungi test specifici:

```ts
compatibleMealIngredients({ diet: "senza glutine" }, "breakfast")
```

deve contenere almeno:

* pane senza glutine;
* fette biscottate senza glutine;
* biscotti senza glutine;

salvo incompatibilità con un secondo vincolo.


Non deve essere possibile che uno usi la closed allowlist e l'altro no.

# 8. NON CONFONDERE LATTOSIO E ALLERGIA AL LATTE

Mantieni distinta la semantica:

## Intolleranza al lattosio

Vincolo:

`lactose`

## Allergia alle proteine del latte / caseina / latte

Vincolo:

`milk`

Un prodotto “senza lattosio” NON deve essere considerato automaticamente sicuro per un'allergia alle proteine del latte.

Il validatore già distingue in parte `LACTOSE_RULE` e `MILK_RULE`: preserva e rafforza questa distinzione.

# 9. CONSENSO SALUTE

Verifica la classificazione GDPR.

La stessa informazione sanitaria non deve cambiare trattamento semplicemente perché viene scritta nel campo Dieta invece del campo Allergie.

Esempio:

* “senza glutine” come scelta alimentare personale;
* “sono celiaco” come informazione sanitaria;

non sono semanticamente identici.

Definisci esplicitamente e testa quando deve essere richiesto `aiHealthConsent`.

Non modificare la policy privacy in modo arbitrario: documenta la decisione adottata.
